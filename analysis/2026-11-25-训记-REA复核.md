## 4. 数据模型：已观察结构与独立设计分开

### 原生传输对象

R4–R8 得到下面的字段关系：

```text
WorkoutPlan
  id, title, dateStr, start, end
  movement: List<MovementItem>
    key, label, type, restTime, warnRestTime
    singleSide: Boolean, ss: Integer, cardioAccessory
    sets: List<SetItem>
      weight: String, leftWeight: String, reps: String
      time: int, done: boolean, unit: String
```

引用追踪在 JADX 的 using-node 范围内只返回 `GarminModule`；反编译确认 `parseWorkoutPlan` 使用 Gson 将 JSON 解码为该对象。因此它是 **Garmin 桥接传输结构的证据**，不能直接宣称为训记主训练模型。`weight/reps` 为字符串也不意味着 Leanora 应采用相同存储方式；`leftWeight` 不能证明左右侧容量的计算规则。

### 业务存储字面量

本次复核 21 条建表和 7 条迁移字面量，与[2026-10-20 报告](训记与薄荷-开发参考.md)一致。重点表包括：

| 表 / HBC 字符串 ID | 可观察职责 | 边界 |
|---|---|---|
| `movements` / #82005 | 动作、分类、单位、肌群、来源 URI 等 | 未取得真实设备表数据 |
| `templates` / #82010 | 模板内容、规则、文件夹归属、排序、版本 | `movement/rules` 为 TEXT；完整嵌套合同未知 |
| `localtrains` / #80212 | 日期、起止、标题、动作内容、模板关联与备注 | 不知道所有运行时字段和迁移结果 |
| `platformPlans` / #65701 | 指定日期、计划和训练日类型 | 不据此推断周期推进策略 |
| `platformplanrules` / #82007 | 计划、模板、动作对应规则 | 规则算法未还原 |
| `prtables` / #80214、`histindex` / #82004 | 纪录/历史索引线索 | 不证明 PR 的计算口径 |
| `folders` / #82003 | 模板组织、排序和版本 | 删除及分享规则未验证 |

Leanora 应沿用自己的 Codable 聚合和 SwiftData 存储，按独立设计增加周期与规则模型；不直接执行竞品 DDL，不复制未知的 JSON 合同。

源码基线为 `e9203f67dfab8f7f1ea31af339f4c09644b5792d`。本次只做文件和目录数据检查，没有重新运行 App 或回归测试。

| 检查项 | 当前实际情况 | 判断 |
|---|---|---|
| 主导航 | 历史、动作、饮食、我的；今日内容在历史顶部 | 已完成，保持结构 |
| 训练 | 模板/周计划、目标与实际值分离、组类型、RPE/RIR、超级组、计时、历史复用、模板更新 | 已有基础，重点改录入效率 |

| 训练中动作菜单 | 上移、下移、移除；未发现替换入口 | 增加保留历史和目标边界的替换流程 |

| 食品与指南 | 500 条食品、6 套食物搭配；训练/饮食各 12 篇指南 | 本轮保留，训练研究不自动扩大成饮食功能重写 |
